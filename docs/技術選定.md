# 技術選定

バーコードを読み取って食べたものを記録し、栄養管理するWebアプリの技術選定の記録。

## 要件

- 商品のバーコードを読み取り、食べたものを記録できる
- 記録した内容から栄養（カロリー・PFC・食塩など）を管理できる
- スマホのブラウザで使う
- データはサーバー（自宅サーバー）に保存する
- 利用者まわり（複数ユーザー・ログイン）は後回し。まずは上記を動かすことを優先する

## 決定事項

### 対応端末

- **iPhone を主に想定しつつ、Android でも動くようにする**

### バーコードの読み取り方式

- **スマホ側（ブラウザ）で、カメラ映像からリアルタイムに読み取る**
  - カメラをかざすだけで読み取れる体験を優先した
- iPhone の Safari はブラウザ標準の `BarcodeDetector` API に非対応のため、ライブラリ（`zxing-wasm` など）を使う。これで iPhone / Android で同じように動く
- カメラ映像の取得（`getUserMedia`）は **HTTPS が必須**

| 方式 | 良い点 | 悪い点 |
|---|---|---|
| スマホ側でリアルタイム読み取り（採用） | かざすだけで即読める／画像を送らないので速い／サーバーが軽くなり言語を選ばない | iPhone は標準APIがなくライブラリが必要／HTTPS 必須 |
| 写真を撮ってサーバーで解析 | 実装が一箇所で端末差がない／HTTPS なしでも動く | 撮影→送信→待ちの手間／毎回数MBの画像を送る |

### 公開方法

- **自宅サーバー ＋ Cloudflare Tunnel ＋ 自分のドメイン（Cloudflare 管理）**
  - 外出先からも使うため、外部からアクセスできる必要がある
  - ポート開放なしで HTTPS 公開できる
- 一般公開になるので、ログイン機能を作るまでの間は **Cloudflare Access** でアクセスできる人を制限する（許可したメールアドレスのみ）

## サーバーの言語とデータベース（評価済み・未確定）

### 経緯

- 最初に TypeScript（Node）を提案した。サーバー側の npm 依存はサプライチェーン攻撃（依存パッケージの乗っ取り）が怖いので避けたい、という理由で見送り
- 次にサプライチェーンの軸だけで Go を提案した。「Go に有利な情報しか出していない」「SQLite を勝手に確定扱いしている」と指摘を受け、評価軸を広げてやり直した
- 2026-10-16〜17 に、候補ごとの調査（Go / Deno・Bun / Rust / C#・Java/Kotlin / Python・その他 / DB）→ 統合 → Codex による批判的レビュー → 指摘の事実確認、の順で評価した
- 統合段階の草案は Go＋PostgreSQL を推していた。Codex はこれに対し「Go に有利な比較条件が混ざっている」「サプライチェーン対策の効果を過大評価している」と指摘した。指摘 29 件を事実確認した結果、採用 24 件・一部採用 5 件・却下 0 件

### 結果（暫定）

上位 3 つは実質的に同点で、点差は採点の揺れより小さい（34 軸、重み付きで満点 470）。

| 構成 | 合計 | 採点を ±1 動かしたときの幅 |
|---|---:|---|
| C# 14 / .NET 10 LTS ＋ ASP.NET Core ＋ EF Core ＋ PostgreSQL 18 | 364 | 352〜379 |
| Python 3.14 ＋ Django 5.2 / 6.2 LTS ＋ SQLite | 359 | 343〜370 |
| Go 1.27（標準ライブラリ中心）＋ pgx（PostgreSQL）か SQLite | 358 | 338〜362 |

- 暫定の第一候補は C#。理由は点差ではなく、Microsoft 以外の本番依存を Npgsql 1 つに抑えたまま、将来の自前ログイン・CSRF 対策・マイグレーションを自作せずに済むこと
- サプライチェーンの群だけを見ると Go が最も高い（開発終了が決まった Deno を除く）
- 逆転条件
  - 自前ログインを作らず Cloudflare Access を使い続け、さらに開発機の保護を最優先するか、サーバーが低スペックなら → Go
  - Python が書けて MVP の速さを優先するなら → Django
  - 画面と同じ TypeScript を最優先するなら → Node.js を実測込みで評価し直す（暫定 332 点）

### データベース

- 認証の有無では決めない。この規模・単一ホストなら SQLite も PostgreSQL も要件を満たす
- 言語と一緒に決める
  - C# なら PostgreSQL（SQLite の経路だと、1 人が保守するネイティブ部品と、ビルドのたびに読み込まれる `.targets` が本番依存に加わるため）
  - Django なら SQLite（OS の SQLite の版の確認が条件）
  - Go ならどちらでもよい
- 保存先が NAS（NFS・SMB）なら SQLite は使えない

### 評価で分かった、前提の修正

- 画面側に悪意ある JS が混ざると、ログイン中の利用者として API を呼べる（CSP や HttpOnly Cookie では止まらない）。通信先を絞ればデータの持ち出しは防げるが、記録の改ざんや削除は防げない
- Go でも、テストを実行すると（`go test`）依存のコードは動く。どの言語でも開発環境・CI の隔離が必要
- 乗っ取りの機会に効くのは、依存の「個数」より、本番経路に入る「独立した公開主体の数」
- Deno はチームが Cloudflare に合流し、約 1 年の修正提供の後にランタイムの開発を終える方針（OSS としては残る）
- 利益相反: 評価を書いた Claude の開発元 Anthropic は Bun を所有している

- 下の質問に答えてもらう
- 上位 2〜3 構成で小さな試作（認証、他人のデータへのアクセス拒否、欠損値の集計、履歴の保持、復元）を作り、自宅サーバーでメモリなどを実測する

### 結論を左右する質問（優先度順）

1. 自前のログインを作るか。Cloudflare Access（無料枠は 50 人まで）を使い続けるか
2. 最も避けたい被害は、開発機の秘密情報の流出・食事データの漏えい・改ざん・消失のどれか
3. 書ける言語と、MVP の速さをどれだけ優先するか
4. 自宅サーバーの CPU アーキ、空きメモリ、保存先（ローカルディスクか NAS か）、OS
5. 画面と同じ TypeScript で書くことに、他を譲ってでも価値を置くか
6. 許容できるデータの損失時間（RPO）と停止時間（RTO）
7. DB を Grafana や Metabase から直接読みたいか
8. 学習価値（キャリア）を選定に入れるか
