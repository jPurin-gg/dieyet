## 要件

- 商品のバーコードを読み取り、食べたものを記録できる
- 記録した内容から栄養（カロリー・PFC・食塩など）を管理できる
- スマホのブラウザで使う
- データはサーバー（自宅サーバー）に保存する
- 利用者まわり（複数ユーザー・ログイン）は後回し。まずは上記を動かすことを優先する

## 決定事項

### 対応端末

- **iPhone を主に想定しつつ、Android でも動くようにする**

### バーコードの読み取り方式

- **スマホ側（ブラウザ）で、カメラ映像からリアルタイムに読み取る**
  - カメラをかざすだけで読み取れる体験を優先した
- iPhone の Safari はブラウザ標準の `BarcodeDetector` API に非対応（iOS 27.2 時点でも既定で無効）のため、ライブラリ（`zxing-wasm` など）を使う。これで iPhone / Android で同じように動く
- カメラ映像の取得（`getUserMedia`）は **HTTPS が必須**
- 確定前に最初にやること（言語に関係なし）: **実機の iPhone で、ホーム画面に追加した PWA のカメラ読み取りを 1 週間試す**（カメラ許可のダイアログが起動ごとに出る既知の問題、近接時の合焦、zxing-wasm のデコード時間、JAN の誤読率）。デモの成否を最も左右するのはここ

| 方式 | 良い点 | 悪い点 |
|---|---|---|
| スマホ側でリアルタイム読み取り（採用） | かざすだけで即読める／画像を送らないので速い／サーバーが軽くなり言語を選ばない | iPhone は標準APIがなくライブラリが必要／HTTPS 必須 |
| 写真を撮ってサーバーで解析 | 実装が一箇所で端末差がない／HTTPS なしでも動く | 撮影→送信→待ちの手間／毎回数MBの画像を送る |

### 公開方法

- **自宅サーバー ＋ Cloudflare Tunnel ＋ 自分のドメイン（Cloudflare 管理）**
  - 外出先からも使うため、外部からアクセスできる必要がある
  - ポート開放なしで HTTPS 公開できる
  - Cloudflare がエッジで TLS を終端し、HTTP の中身を扱う（Tunnel 配下のアプリは平文 HTTP）
- 一般公開になるので、ログイン機能を作るまでの間は **Cloudflare Access** でアクセスできる人を制限する（許可したメールアドレスのみ。無料枠 50 人）。ログイン機能ができた後も、管理画面だけは Access の後ろに置く
- Access を使う間も、アプリ側で Access の JWT（aud / iss / exp、鍵の更新）を検証し、ヘッダのメールアドレスをそのまま信用しない
- Cloudflare の無料機能で防御コードを減らせる範囲は限られる: 無料のレート制限はルール 1 本・IP 単位・10 秒窓・Path 条件のみ。利用者単位の回数制限や有料 API の予算はアプリ側で作る。Turnstile はサーバー側検証が必須

### ログイン

- **ログインは外部の ID プロバイダに任せる（OIDC / OAuth2）。アプリ内にパスワード認証は作らない**（2026-10-19。10-18 の「自前で作る」を変更）
  - 理由: 見せたいのはアプリの出来であり、ログインの実装ではない。知らない人も使えるようにしつつ、事故が致命的な部分（パスワード保管、総当たり対策、リセット）を書かない
  - 初版は Google 1 つで始める案が有力（openid / email / profile だけなら Google の審査は不要で、テスト状態の 100 人上限もかからない）。GitHub は OIDC ではなく OAuth2＋`/user` の別経路。LINE は Web ログインの ID トークンが HS256 で、email は申請制、チャネルの Published 化は不可逆なので初版から外す
  - 利用者の主キーは **(issuer, sub)**。email は表示用で、email による自動のアカウント統合は禁止（nOAuth 型の乗っ取り対策）。複数プロバイダの紐付けはログイン済みセッション内の明示操作だけ
  - ホームラボ共通の SSO が欲しくなったら、自前の ID プロバイダを同じ OIDC で追加する（知らない人の自己登録: Zitadel にはある。Authelia には無い。Pocket ID は v1.5.0 から設定で可能だが公開インスタンスでの開放は公式が非推奨）
  - アプリ側に残るもの: OIDC クライアント（state / nonce / PKCE）、セッション（発行・失効・固定化対策・鍵更新・Cookie 属性）、CSRF 対策、認可（本人のデータか）、ログアウト、アカウント削除、プロバイダ喪失時の復旧（第 2 プロバイダの事前紐付け、データ書き出し）。**Go では 100〜200 行＋テスト 10 件前後の手書きになる**（「数十行」「どの言語でもほぼ同じ」は誤りだった。C# は Microsoft 一次提供の OIDC ハンドラと Cookie 認証がある）
  - Google の OAuth クライアントは 6 か月無使用で自動削除されるので監視する
  - 知らない人が使う場合は他人の個人データ（食事記録）を預かるので、アカウント削除やプライバシーポリシーも設計時に検討する

### ログインの再検討と、筋トレ管理アプリとの統合（2026-10-20、未決定）

ユーザーから新しい前提が 2 つ示された。

- **堅牢にするつもりはない**。必要なのは「特定の人を区別できること」で、ニックネームが重複しうる（「ぷりん」を名乗る人が周りに複数いる）ので、**ニックネーム＋合言葉**で人を判別する想定だった
  - 「区別」はニックネームの一意化（重複なら番号を付ける、内部は番号で管理して表示名は自由）で、「本人確認」は合言葉で、と分けて考える。合言葉は技術的にはパスワードなので、最低ラインは守る: ハッシュ保存（`x/crypto` の bcrypt か argon2id）、試行回数の制限、HTTPS。本物のパスワードの使い回しをしないよう利用者に伝える。忘れた場合はメールが無いので管理者が手でリセット
  - コード量は Google ログインとほぼ同じ（登録・ログイン・ハッシュ・試行制限で 150〜200 行）。違いは、Google の設定が要らず利用者にアカウントが要らない代わりに、秘密を自分で預かること
  - この温度感なら、DB の行単位の権限（共有 PostgreSQL＋RLS）や追記専用トリガーは不要。残すのは「日次バックアップをアプリが消せない場所に置く」程度
  - 10-19 の「外部の ID プロバイダ（OIDC）に任せる」は、この前提で再検討する
  - ユーザー案: 登録とログインを分けず、画面 1 つで「初めての組み合わせなら新規作成」にする。画面を分けない点は採用。ただし「組み合わせが初めてなら新規作成」のままだと、合言葉の打ち間違い・忘れが「無言で空のアカウントができる」形になって見えなくなり、ニックネームと合言葉が両方かぶった 2 人が同じアカウントを共有してしまう
  - **採用する流れ（ユーザーの元の案のとおり）**: 画面 1 つ。ニックネームの重複は許す。身元は「ニックネーム＋合言葉」の組み合わせで、内部は番号で管理。**組み合わせが既存なら、その人としてログイン。初めての組み合わせなら、確認なしでそのまま新しいアカウントを作って入る**（「はじめまして、◯◯ として登録しました」とだけ表示）。ニックネームを一意にする案、既存ニックネーム＋合言葉不一致のときに確認を出す案は、どちらも取り下げた
  - 受け入れる点（2026-10-20、「今のところ」）: 合言葉の打ち間違いや忘れで、記録の無い新しいアカウントができる。同じニックネーム＋同じ合言葉は同じ人として扱われる。記録ゼロのアカウントの自動削除は実装したが既定では無効（`DIEYET_PRUNE_IDLE_DAYS`）。`users` を他のアプリと共有すると、食事の記録が無くても筋トレの記録がある人を消してしまうため。他の利用者から 2 人の同名を見分ける必要が出たら（比較機能など）、表示名に番号を付ける
  - 端末にログイン状態を長く覚えさせて（Cookie の期限を数か月）、入力の機会自体を減らす
- **別に作っている筋トレ管理アプリと、いずれ統合・連携したい**。同じ人の食事と筋トレを結びつけるなら、利用者の管理は 1 か所であるべきで、ログインと DB の両方に効く

| 最終形 | ログイン | DB | 特徴 |
|---|---|---|---|
| A. 1 つのアプリに統合（Go の 1 プロセスに食事と筋トレのモジュール） | 1 つ。合言葉方式で問題なし | SQLite ファイル 1 つ | 最も軽く簡単。1 回のログインで両方。横断の集計も同じ DB |
| B. 別アプリのまま API で連携 | どちらかが利用者を持ち、もう一方が信用する。または Google で共通化（同じ Google アカウントなら `sub` が共通） | それぞれ SQLite | アプリが独立。横断の集計は API 越し |
| C. 別アプリのまま DB を共有 | 共通の利用者テーブル | 共有 PostgreSQL | 言語が違っても共有できる。横断の集計が楽。常駐プロセスが 1 つ増える |

- どれにするかは、筋トレ管理アプリの現状（言語・DB・進み具合）で決まる
- **ユーザーの意向（2026-10-20）: C に近い形。アプリは別々のまま、DB を 1 か所につなぎ、それぞれが必要なデータだけ読んでフィードバックを返す**
  - DB の選択肢は 2 つ。(1) 同じ SQLite ファイルを 2 つのアプリで共有: 両方が同じマシン（同じ LXC）で動き、ファイルがローカルディスクにあることが条件。最も軽い。書き込みは同時に 1 つ、両方の SQLite が 3.51.3 以上であること。(2) PostgreSQL を共有: ネットワーク越し・言語を問わない。PG が 1 つ常駐
  - テーブルの持ち主を分ける: `users`（と `sessions`）は共有。食事は `food_`、筋トレは `training_` の接頭辞。自分のテーブルだけ書き、相手のは読むだけ。マイグレーションは各アプリが自分の分だけ持つ
  - `sessions` も共有し、2 つのアプリを同じホスト名の下（`/food/`、`/training/`）で公開すれば、ログインは 1 回で済む
  - dieyet 側の対応: データを入れる前にテーブル名に `food_` を付ける（実施済み）。PostgreSQL にする場合も DB まわりは `internal/store/` に閉じている
- **前提の更新（2026-10-20）: 筋トレ管理アプリはすでに大きく、デプロイ済みで改善中。後から作るのは dieyet のほう。よって dieyet が筋トレアプリに合わせる**
  - 利用者とログインは筋トレアプリのものを使う想定（dieyet のニックネーム＋合言葉ログインは、筋トレ側にログインがあれば不要になる）
  - DB は筋トレアプリのものに `food_` のテーブルを足す形が自然。筋トレ側はそれを読んでフィードバックを出す
  - dieyet の役割は「栄養を楽に取り込む入口」に絞る。分析・表示は筋トレ側に寄せられる
  - 形の候補: A. 筋トレアプリの DB に直接書き、ログインは筋トレ側のセッションを見る。B. dieyet は独立サービスで、筋トレ側が API で記録を取りに来る。C. 筋トレ側と同じ言語なら一機能として取り込む
  - 今の実装で残るもの: 読み取り画面、商品マスタ、「不明は 0 にしない」集計、Open Food Facts の照会、記録。入れ替わるもの: ログイン（`internal/auth/`）と DB 接続（`internal/store/`）

### 筋トレアプリとのつなぎ方（2026-10-20、DB は決定・ログインは確認中）

- 筋トレアプリの構成: **Node.js（画面）＋ Go（API）＋ PostgreSQL**。dieyet とは**別の LXC** で動く
- **DB: 筋トレアプリの PostgreSQL に相乗りする（決定）**。別 LXC なので SQLite ファイルの共有は不可。PostgreSQL に `food` スキーマを作り、dieyet はそこだけ書く（`food.products`、`food.logs`、`food.schema_migrations`）。`users` と、フィードバックに必要な筋トレ側のテーブルは読むだけ
  - `dieyet` 用の DB ロールを作り、権限は `food` スキーマの全部＋必要なテーブルの SELECT だけ
  - PostgreSQL は LAN のアドレスで待ち受け、`pg_hba.conf` で dieyet の LXC の IP とロールだけ許可。パスワードは dieyet 側の環境変数
  - dieyet 側: `internal/store/` を SQLite から PostgreSQL（pgx）に差し替える。`food.logs.user_id` には筋トレ側の利用者番号を入れる
- **ログイン: 筋トレ側も同じ方式（ニックネーム＋合言葉、初めての組み合わせなら新規作成）になる（決定）**。共有するのは利用者データ（`users`）だけで、各アプリは自分のテーブルを `user_id` でつなぐ
  - 両方のアプリで合わせるのは 3 つだけ: `users` の形（`id`、`nickname`、`pass_hash`、`created_at`、`last_login_at`）、合言葉のハッシュ形式（argon2id の PHC 文字列。どの言語のライブラリでも作成・検証できる）、ログインのルール。詳細は README の「筋トレ管理アプリと共有するもの」
  - セッションはアプリごとに別（dieyet は `food.sessions`）。ホスト名が違えば Cookie は共有できないので、各アプリで 1 回ずつログインする。同じホスト名の下にまとめれば共有もできる
  - `users` の持ち主は筋トレアプリ。dieyet は `users` が無い DB（テスト・単体）でだけ同じ形で作る。dieyet の DB ロールには `users` の SELECT / INSERT / UPDATE / REFERENCES（外部キー用）と `food` スキーマの所有だけを与える。この権限だけで起動・ログイン・記録ができることはテスト（`TestLeastPrivilegeRole`）で確認している
  - 実装済み（2026-10-20）: `internal/store/` を PostgreSQL（pgx）に書き換え、PostgreSQL 18 に対するテストが通っている

### 製品の焦点（2026-10-20）

- **「栄養を調べるのが面倒」「入力するのが面倒」を潰すことに特化する**。バーコード読み取りは入口で、価値は「5 つの数字を自分で調べて打たなくていい」こと。Open Food Facts で日本の商品が出るのは 57% 程度なので、放っておくと半分近くが手入力になる
- 効き目の順: (1) 成分表示を撮るだけで入力（写真を LLM の画像 API に送って 5 項目を抜き、確認して保存。1 枚あたり数円、利用回数の上限が要る）、(2) 読んだ商品はみんなの共有 DB に残す（実装済み）、(3) 「前と同じ」・最近食べたもの・よく食べるもの、(4) バーコードなしの食事は汎用食品の検索（文科省の成分表 2,538 品を内蔵）、(5) Open Food Facts の下書き（実装済み）、(6) 量の入力を楽に（「1 個」「半分」「2 本」のボタン、g 入力）
- (1) と (4) を足すと「調べる」も「打つ」もほぼ消える。ログインや DB の細部より、ここに労力を回す

### コードの公開

- **コードは GitHub で公開する。人に見せることもある**（2026-10-19）
- 言語への影響: 公開を前提にしても順位は動かない。「C# は DI・属性・ORM の規約を知らないと読みにくい」「日本の Web 系では Go が目立つ」「学習価値を戻すと Go 寄り」はいずれも誤りか意見だった（学習価値を戻して上がるのは Django。求人数の公開データでは C# 5.8% で Go はトップ 10 外、提示年収は Go が 1 位）。志望先が決まってから学習価値を入れる
- 公開リポジトリの衛生管理（どの言語でも同じ）
  - 秘密情報を絶対にコミットしない。GitHub の無料機能（Dependabot、CodeQL、シークレットスキャン）を有効にする。ただしこれらは未知の悪性依存や認可ミスは検出しない
  - PR の検証は GitHub ホストの runner だけで行う（自宅に self-hosted runner を置かない）。`pull_request_target` / `workflow_run` を未信頼の PR と組み合わせない。Actions は SHA 固定、`permissions` は `contents: read` を既定。配備は main への push で動く別ワークフロー＋environment の承認。自宅への配備は pull 型（自宅側が GHCR / Releases から取りに行く）
- コードで評価されるのは、構造の明快さ、テスト、CI、セキュリティ対策（CSP、OIDC）、設計を説明した README。README に「自作したセキュリティ関連コード（セッション、CSRF、マイグレーション、認可）の一覧と対応するテスト」を載せる
- 再現可能ビルドが確かめられるのは「所定の入力から同じ成果物が得られること」だけ。配備後の差し替えや DB の改ざんは証明しない。改ざん対策は配備・稼働時の検証（バイナリの digest 照合、署名、DB の履歴）で担保する

### 自宅サーバー

- 普通の PC（x86）のノートパソコンに **Proxmox VE** を入れている。メモリは 16GB の見込み。処理性能には自信がない（2026-10-19 の回答）
- ローカル LLM を動かす予定はほぼない（LLM を使う場合は外部 API で呼ぶ）
- 保存先（ローカルディスクか NAS か）は未確認
- **他にも多くのアプリを動かす予定なので、各アプリは軽いほどよい**（2026-10-19）。「動くかどうか」ではなく「どれだけ軽いか」で評価する
- 待機時メモリの実測（2026-10-19。WSL2 上。自宅サーバーでは未実施）
  - 同一条件（Cookie セッション＋OIDC＋SQLite、2,000 リクエスト並列 20）: **Go 19MB**、**.NET 10（生 ADO.NET）115〜120MB**（私有約 46MB）、.NET 10＋EF Core 163〜174MB（2 倍遅い）。Native AOT は Cookie / OIDC 非対応
  - 別条件: Django 1 ワーカー 85MB（2 ワーカー 135MB）、Node 75〜85MB、PocketBase 31〜48MB。PostgreSQL は未測
  - 絶対量で見ると、1 アプリあたりの差は 40〜80MB（16GB の 0.25〜0.5%、10 アプリで 0.4〜0.8GB）
- 軽くするための工夫（言語に関係なし）: DB はアプリごとに PostgreSQL を立てるより、SQLite か、全アプリで 1 つの PostgreSQL を共有するほうが軽い。Proxmox 上では VM より LXC のほうが軽い（ただし LXC はホストのカーネルを共有し、VM と同じ隔離境界ではない）
- Proxmox 公式の Docker に関する記述は 2025-11 以降は条件付き（オーケストレーションやライブマイグレーション、最大の隔離が要るなら VM）。PVE 9.1 では OCI イメージからのアプリコンテナが tech preview。「Docker が要らないから Go」という加点はしない
- Go の単一バイナリは置くだけで動くが、静的リンクなので Go の修正（2026 年は 9 日付のセキュリティ修正）のたびにアプリ数ぶんの再ビルド・再配備が要る。月次の自動 CI を前提にする。.NET の framework-dependent 配備なら apt の更新が全アプリに入る
- ノートパソコンをサーバーにする場合の運用（蓋を閉じてもスリープしない、電源につなぎっぱなし、再起動後の自動起動）は、言語に関係なく後で設定する

### 一番避けたい被害

- **開発用 PC の秘密情報（パスワード、SSH キー、GitHub のトークンなど）を盗まれること**と、**データを書き換えられたり消されたりすること**（2026-10-19）
- どちらも、言語の選択より次の対策が効く。**言語より先に決める**（どの言語でも必須）
  - 開発用 PC の隔離: 長期トークンを置かない VM / devcontainer（ホームディレクトリ・SSH agent・Docker ソケットを渡さない）で開発する。画面側の npm も同じ環境で動かす。クローンしたリポジトリは VS Code の制限モードで開く。拡張の棚卸しと許可リスト化。fine-grained の短命トークン。AI エージェントの自動承認フラグを使わない。Go でも `go test` / `go run` / gopls は依存コードを動かすので同じ隔離を適用する
  - 公開用 LXC のネットワーク分離: 専用ブリッジ / VLAN に置き、アプリは cloudflared からのみ到達可能にする。公開環境から開発 VM・Proxmox 管理面（8006）・バックアップ先への通信を遮断する
  - 改ざん・削除: 書き込みのたびに本人のデータか確認する（所有者はセッションから決める）。記録は追記専用にし、削除は墓石行の追加にする。バックアップは整合性のある取得（SQLite の backup API / `VACUUM INTO`、pg_dump）→ 暗号化 → **アプリから削除できない先**（PBS の `Datastore.Backup` のみのトークン、または R2 の書き込み専用トークン＋bucket lock）へ、別の障害領域に置き、失敗検知つきで定期実行し、復元を試験する。アプリが乗っ取られれば履歴テーブルも同じ権限で書き換えられるので、履歴だけでは防げない
  - 画面側の依存を減らし CSP を厳しくすることは、持ち出しの軽減にはなるが防げない。改ざんや削除も防げない

### Go で進める場合の代償（これを引き受けることが条件）

1. OIDC クライアント・セッション・CSRF・認可・マイグレーション・商品マスタの保守画面はほぼ手書き（100〜200 行＋テスト 10 件前後）。go-oidc を使うなら state・nonce・PKCE・セッション ID 再生成・サーバー側失効・`__Host-` Cookie・`http.CrossOriginProtection` の配線を受け入れテストに明記する。標準ライブラリだけで書く構成（認可コードフローでトークンエンドポイントから直接受け取る ID トークンは TLS で保護されるので、iss / aud / exp / nonce の照合で足りる）なら本番の第三者は DB ドライバ 1 主体になる
2. Go のセキュリティ修正のたびに全アプリを再ビルド・再配備する CI を初日に作る（golang イメージの digest と go.mod の go 行を Renovate で上げ、govulncheck を通し、自動で配備）。この CI を作る気が無いなら、ランタイム共有型（.NET、Node、Python）のほうが手数がアプリ数に比例しにくく、言語を再検討する価値がある
3. 標準ライブラリの既定値を雛形で潰す: `http.Server` のタイムアウト 4 種と `MaxBytesHandler`、外部呼び出しの `http.Client` のタイムアウトと context 期限。`CGO_ENABLED=0`、`GOTOOLCHAIN=local`、`GOFLAGS=-mod=readonly` を開発機・CI・本番で固定し、許可リスト外のモジュールが増えたら CI を落とす
4. 「不明」と「0」の区別: 栄養値は `*float64`（または専用型）で受ける。`encoding/json/v2` を `RejectUnknownMembers(true)` で使う（v1 なら `DisallowUnknownFields`＋`MatchCaseSensitiveNames`）。必須 5 項目の欠落は検証層で 400。保存は整数（mg、0.1 kcal）、丸めは表示直前。日別集計は「既知の合計・不明件数・完全か」の 3 値
5. 所有者条件の抜けを機械で防ぐ: リポジトリ層で UserID を専用型の必須引数にし `*sql.DB` を直接触らせない。CI で各クエリが user_id を持つことを検査。エンドポイント×他人 ID の拒否テスト（20 件程度）
6. 「依存最小」は本番バイナリに限定し、秘密情報の無い CI で golangci-lint か staticcheck＋errcheck / bodyclose / rowserrcheck / noctx と gosec、govulncheck を関門にする。AI が提案したインポートは pkg.go.dev で公開主体と初版日を確認してから `go get`
7. 時刻は UTC の RFC 3339 文字列か Unix 秒の整数で自分で明示保存し、DB ドライバ既定の `time.Time` 変換に依存しない

### Go 以外を選ぶべき条件

- **C#（.NET 10 LTS、ASP.NET Core Minimal API、PostgreSQL 経路）**: 次の 3 つがそろえば C#。(1) OIDC クライアント・セッション・CSRF・マイグレーション・保守画面を手書きしたくない（Microsoft 一次提供の OIDC ハンドラ、Cookie 認証、Data Protection の鍵更新、EF Core のクエリフィルタと差分マイグレーション）。(2) 月次の再ビルド CI を作る気が無く、LXC に `aspnetcore-runtime-10.0` を apt で入れて自動更新に任せたい。(3) 1 アプリ 115〜120MB（EF Core なら +40MB）を払える。条件: PG 経路（SQLite 経路は SQLitePCLRaw の `.targets` と `.so` を本番依存に加える）、NuGet の署名検証（Linux での動作は要実機確認）、`packages.lock.json`、テストは MSTest、2028-11 までに .NET 12 へ移行。Minimal API＋record なら同機能の Go より短く属性も不要
- **Django（Python 3.14、Django 6.2 LTS、SQLite）**: Python を書けて MVP の速さを優先する場合（修正後の重みで Django 390 / C# 386 / Go 381）、または共有の商品マスタの監修画面（Django admin）を初版の必須要件にする場合。条件: 1 アプリ +70MB、月例のセキュリティ追従、uv の `no-build`＋`exclude-newer`＋`--frozen`、OIDC クライアントを標準ライブラリで書くか allauth を入れるか決める、OS の SQLite 版を避けて uv 管理の CPython を使う、`/admin` は Access の後ろ
- **TypeScript（Node 26 LTS、node:sqlite、openid-client）**: 「オフラインで動く記録・集計・同期のロジックを画面と 1 回だけ書きたい」に「はい」の場合（同点圏に入る。ただし先頭は C#）。条件: npm 12 か pnpm 11、minimum release age、`strict-allow-scripts`、CI で `npm ci`＋`npm audit signatures`、PR に秘密を渡さない、1 アプリ 75〜85MB。Bun は LTS 無し・Security Advisories 非公開・Anthropic 所有（利益相反）で本命にしない
- **既製バックエンド（PocketBase）**: 「数週間早いデモ」と「認証・CRUD・管理画面を書かない」を、公開主体 17・1 人保守の pre-1.0・NULL を持てない数値列・SQLite 固定より上に置き直す場合だけ

### データベース

- 認証の有無では決めない。この規模・単一ホストなら SQLite も PostgreSQL も要件を満たす
- **Go なら SQLite（ncruces/go-sqlite3、`CGO_ENABLED=0`）を既定にする。ただし条件付き**。満たせないなら PostgreSQL
  1. 保存先はローカルディスク（NAS の NFS / SMB では使わない）
  2. リポジトリ層に集約し、所有者条件の抜けを CI とテストで機械的に防ぐ（上の代償 5）
  3. 記録テーブルは追記専用（削除は墓石行の INSERT。UPDATE / DELETE は BEFORE トリガーで `RAISE(ABORT)`）。履歴は本体と同じトランザクションで書く
  4. バックアップは `VACUUM INTO` → 暗号化 → アプリから削除できない先へ（「一番避けたい被害」を参照）
  5. `SetMaxOpenConns(1)`（または読み書き別プール）、`busy_timeout`、`_txlock=immediate`、WAL
  6. マイグレーションは SQL スクリプト（SQLite の 12 段階手順）をレビューしてから適用し、試作で 1 回実際に書いて巻き戻しをテストする
  7. ncruces の保守が止まったら固定した版を使い続けるかフォークする方針を README に書く（3 つの Go の SQLite ドライバはどれも実質 1 人保守で、ncruces と modernc は機械生成コード）
- **全アプリで共有する PostgreSQL を選ぶべき場合**: (a) 「改ざん・削除」を言語ではなく DB 層で守りたい（アプリ用ロールは DML のみ、全利用者テーブルに RLS、リクエストごとに `SET LOCAL` で利用者 ID、履歴テーブルは INSERT のみ許可して別ロール所有のトリガで書く）。(b) Grafana / Metabase から DB を直接読みたい。(c) 他のアプリのために共有 PG を立てる予定が既にある。その場合は pgx、アプリごとのロールとスキーマ。アプリごとの PostgreSQL は推奨しない
- SQLite 既定への最も強い反論: ユーザーが最優先に挙げた被害は「改ざん・削除」であり、SQLite はアプリと同じプロセスで動くので、アプリが乗っ取られれば履歴もトリガーも同じ権限で無効化できる。PG＋DML のみのロール＋RLS＋履歴の別ロール書き込みなら DB 層で止められる。SQLite でも「乗っ取り後の改ざんを検知して復元できる」状態は作れるが、「乗っ取られたアプリをその場で止める」第 2 層は無い。**改ざん防止を軽さより上に置くなら共有 PG**。中間解として、利用者ごとに SQLite ファイルを分ける（個人記録は構造的に他人のファイルに届かない。商品マスタは共有 DB に分離）
- C# なら PostgreSQL（SQLite の経路だと、1 人が保守するネイティブ部品と、ビルドのたびに読み込まれる `.targets` が本番依存に加わる）。Django なら SQLite（OS の SQLite の版を避けて uv 管理の CPython を使う）

### 評価で分かった、前提の修正

- 画面側に悪意ある JS が混ざると、ログイン中の利用者として API を呼べる（CSP や HttpOnly Cookie では止まらない）。通信先を絞ることは持ち出しの軽減にはなるが防げない。記録の改ざんや削除も防げない
- Go でも、`go test` / `go run` / gopls は依存のコードを動かす（依存コードがリンクされて `init()` 等が動く）。どの言語でも開発環境・CI の隔離が必要
- 乗っ取りの機会に効くのは、依存の「個数」より、本番経路に入る「独立した公開主体の数」
- Deno はチームが Cloudflare に合流し、約 1 年の修正提供の後にランタイムの開発を終える方針（OSS としては残る）
- 利益相反: 評価を書いた Claude の開発元 Anthropic は Bun を所有している
- **Open Food Facts の日本データ**: 日本タグ約 46,400 件のうち GS1 Japan 付番（45 / 49）は 10,522 件、必須 5 項目がそろうのは 57.1%。スキャン数上位は輸入品。「かざすだけで栄養値が出る」は成立せず、**手入力・ラベル撮影の共有 DB と、その監修（確認待ち・出典・版・差し戻し・履歴）がバックエンドの主な仕事になる**
- 包装食品の栄養成分表示（5 項目）は原則義務だが、省略規定がある（表示可能面積おおむね 30cm² 以下、酒類、小規模事業者、製造場所での販売など）。店内調理の惣菜や小規模メーカー品にはラベルが無いのが普通。生鮮は対象外
- 先頭 02・20〜29 の JAN は店内用コード（インストアコード）で店ごとに意味が違う。共有マスタから除外するか店別扱いにする。GTIN は 2019-01-01 以降再利用禁止だが、それ以前に終売した番号は 48 か月後に 1 回だけ再割当できた経過規定があり、過去に再利用された番号は実在しうる
- 学食・外食・自炊に対応するには、文部科学省の日本食品標準成分表（八訂、増補 2023 年で 2,538 食品。出典明記で利用可。成分値は可食部 100g あたりでラベルの基準と違う）を入れて汎用食品を検索できるようにする。無料 Web アプリへの組み込みの届出要否は要確認
- 有料の画像 API（ラベル読み取り）を入れるなら、利用者別の日次上限と全体の月額上限を最初から設計に含める（高解像度・高性能モデルで 1 枚約 $0.019、軽量モデル＋事前縮小で $0.002 前後）

### 検討したが採らない、または条件付きで残す案

- **画面を Cloudflare（Workers の静的アセット）で配信する**: 既にある選択肢として残す。ただし「npm が開発用 PC で動かなくなる」は誤り（開発機では動き続ける。ビルドを Cloudflare に移すとビルド環境と配備権限が攻撃対象になる）。採る場合は CORS・Cookie・CSRF・プレビュー・キャッシュ無効化のコストがある。Go は `embed` でビルド済みの静的ファイルを同梱でき、同一オリジンなら単純
- **オフライン前提（local-first）／バックエンドなしで第 1 版**: 既定にしない。「自宅サーバーに保存」の要件と衝突し、端末の保存領域はバックアップにならない。通常の保存を先に完成させ、オフライン対応は「スキャン→記録のキューイング＋再送（UUIDv7 で冪等）」に限定する。第 1 版から書き出し（JSON / CSV）を入れる
- **Cloudflare Workers＋D1 への全面移行**: 「自宅サーバーに保存」の要件に反し、日本にデータを置く保証が無い。採らない
- **ホームラボ共通の ID プロバイダ**: アプリ側の認証コードを減らす効果は限定的（OIDC クライアント・セッション・認可は残る）。「軽量な ID プロバイダはほとんど Go 製だから Go 寄り」は論理の飛躍で撤回。将来の SSO の選択肢として残す
- **パスキー**: 外部 OIDC にしたので、アプリ側ではなく ID プロバイダ側の選択になった
