問題の中心は、これらのニュースそのものより、**そこから安全性や順位を導く論理**です。

**サプライチェーン保護の評価**

1. **【重大度：高】「フロントエンドは通信を厳格にすれば許容できる」という前提を、十分に訂正していない。**

   悪性JavaScriptが正規の画面に混入すれば、ログイン中の利用者としてAPIを呼び、閲覧可能な食事記録を取得し、更新できます。入力検証・CORS・CSRF対策は、この正規オリジン内の悪性コードを一般には排除しません。HttpOnly Cookieも、Cookieの直接読み取りを防ぐだけで、認証付き操作を防ぎません。

   バックエンドの言語分離には、サーバー上の実行環境や秘密情報を分離する価値があります。しかし、**利用者データの安全まで分離できるわけではない**。この区別なしにバックエンドの依存を細かく採点しても、脅威モデルが欠けています。

2. **【重大度：高】Go の「ビルド時に依存コードが動かない」を、開発工程全体の安全に拡張している。**

   通常の純Goの `go build` が、Cargoのbuild scriptのような依存側の任意フックを実行しない利点は本物です。ただし、`go test`、`go run`、明示的な `go generate`、導入した開発ツールはコードを実行します。レポート自身がテストと自動再ビルドを推奨しています。

   正確には「取得・通常の純Goビルドでの自動実行経路が少ない」。**テストを含む開発・CI環境の隔離はGoでも必要**です。[Goコマンド仕様](https://pkg.go.dev/cmd/go)

3. **【重大度：高】依存の個数を、安全性の代理指標として使いすぎている。**

   155個の小さなcrateと、巨大なランタイムに内蔵された機能群を「155対0」で比較しても、攻撃面の比較にはなりません。「一次提供だから割引」も、公開権限・リリース工程・保守責任がどう集約されているかの説明が必要です。

   数えるべきものは、少なくとも独立した公開権限、保守者への集中、実行される場所、アクセスできる秘密情報、成果物の検証可能性です。**Bun内蔵SQLite、Python標準sqlite3、Go標準暗号処理も、信頼対象から消えるわけではありません。**

4. **【重大度：高】検知・固定・待機期間の効果を混同している。**

   ハッシュ固定やsumdbは、主に内容の同一性や変更検出を扱います。署名・provenanceは出自の検証です。待機期間は発見までの猶予です。`govulncheck` は既知脆弱性の影響を調べる道具です。いずれも「正規保守者が公開した未知の悪性コード」を一般に見抜く保証ではありません。[Go Modules](https://go.dev/ref/mod)、[Go脆弱性管理](https://go.dev/doc/security/vuln/)

   反対に「乗っ取られた正規アカウントには署名が効かなかった」から、署名や公開資格情報の保護を軽視するのも誤りです。攻撃経路ごとに評価すべきです。

5. **【重大度：高】外向き通信制限を、データ持ち出しの決定的な防壁として扱っている。**

   許可したLLM APIへの送信、正規のHTTPレスポンスへの混入など、アプリに許された経路は残ります。プロキシも、環境変数を設定するだけでは迂回できます。直接通信やDNSなどをネットワーク側で制限する必要があります。

   Denoの権限モデルも、同じスレッドのコードは基本的に権限を共有します。依存ごとの隔離ではありません。[Denoのセキュリティモデル](https://docs.deno.com/runtime/fundamentals/security/)

6. **【重大度：中】対策済み構成と、エコシステムの既定動作を混ぜて採点している。**

   Pythonには `no-build` を指定しているのに、ソース配布物のビルドリスクをどこまで残存リスクに算入したのか不明です。.NETもbuild資産などの除外を提案しつつ、既定動作をそのまま減点しています。

   対策は完全ではありません。例えばuvの `--no-build` にも、第一者パッケージやeditable requirementsに関する例外があります。それでも、**既定状態の点と、採用する設定後の点を分ける必要があります**。[uvの仕様](https://docs.astral.sh/uv/reference/cli/)、[NuGetの資産選択](https://learn.microsoft.com/en-us/nuget/create-packages/select-assemblies-referenced-by-projects)

7. **【重大度：高】Goでの認証・マイグレーション自作の損失を過小評価している。**

   「署名付きCookieのセッション」「50〜100行のマイグレーション」は、完成した安全な機能の見積もりではありません。セッション失効、固定化対策、鍵更新、同時実行、途中失敗、適用履歴の整合性まで含める必要があります。

   **依存を減らして増えた自作コードにも、欠陥と保守費用があります。** この負担を算入せず「依存が少ないので安全」と締めるのは不公平です。

**機能・成熟度・保守性に関する誤りと誇張**

8. **【重大度：高】EF Coreのマイグレーションを明確に過小評価している。**

   「モデル差分から自動生成できれば5」と定義してDjangoを5、EF Coreを4にしていますが、EF Coreもモデルとスナップショットを比較してマイグレーションを生成します。提示した基準ならEF Coreも5です。C#はこの一点だけで **425→427** になります。[EF Core公式説明](https://learn.microsoft.com/en-us/ef/core/managing-schemas/migrations/)

   なお「DapperかEF Core」という未確定構成に、EF Coreの利点を丸ごと付けることもできません。構成を分けるべきです。

9. **【重大度：高】Goの互換性と、セキュリティ保守の軽さを混同している。**

   Go 1互換性の約束は大きな利点ですが、古いバイナリを安全に放置できる保証ではありません。レポート自身、短い支援期間と再ビルドの必要性を認めています。

   その一方でOPS-05をGo＝5、.NET＝3とし、「数年放置」をGoの選択理由にするのは矛盾です。.NETの破壊的変更一覧が存在することと、このアプリが更新のたびに修正を強いられることも別問題です。[Go互換性方針](https://go.dev/doc/go1compat)、[.NET支援方針](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)

10. **【重大度：中】Djangoの長期運用案が、不要な短期更新を前提にしている。**

    Django 6.1→6.2という経路だけでなく、既存の5.2 LTSから始める案も比較すべきです。公式表では5.2は2028年4月まで支援対象です。また現行ロードマップでは2028以降のリリース・支援方式の変更が示されており、「今後も2年ごとのLTS」と固定して説明するのは古い情報です。[Django公式ロードマップ](https://www.djangoproject.com/download/)

11. **【重大度：中】「cgoでクロスビルドが壊れる」は誇張です。**

    `mattn/go-sqlite3` はクロスコンパイルを明示的にサポートし、ARM向けの例もあります。追加のCツールチェーンが必要になり、手間が増えるのが正確な説明です。Dockerを使える前提なら、その追加負担を実測すべきです。[ドライバ公式README](https://github.com/mattn/go-sqlite3)

12. **【重大度：中】「生成コード／ネイティブ／DLLはレビューできない、pgxは読める」が粗雑です。**

    生成コードは元ソース、生成器、再現性を追います。DLLは対応ソースと成果物の関係を確認します。手書き7.6万行も、個人が継続監査できるとは限りません。

    比較すべきは「読む気になれる言語か」ではなく、**どの変更を、どの証拠に基づき、継続して検証できるか**です。PostgreSQL本体・コンテナ・OSを計算外にしてSQLiteのCコードだけ問題視するのも不公平です。

13. **【重大度：中】NULLの扱いを言語ランキングに変換しすぎている。**

    `None + 1` が例外になることは、Pythonがコンパイル時に欠損処理を強制する証拠ではありません。Goにもポインタや独自型があります。JDBCの `getDouble()` の挙動は事実ですが、`wasNull()` や適切な取得APIを使う設計もあります。[JDBC仕様](https://docs.oracle.com/en/java/javase/25/docs/api/java.sql/java/sql/ResultSet.html)

    C#の `double?` も、未入力をどう検証するかまでは自動決定しません。**入力・DB・集計・出力を通した欠損の扱い**を、同じ実装課題で比較すべきです。

14. **【重大度：中】「SSRならNode系に引きずられる」は誤りです。**

    Django、ASP.NET Core、PHP、Rails、Goのテンプレートでもサーバー側HTML生成はできます。特定のJSフレームワークを選ぶ話と、SSRという方式の話を混同しています。カメラ読み取り部分だけJavaScriptにする構成も成立します。

**採点そのものの問題**

15. **【重大度：高】比較対象が「言語」でも「完成構成」でもなく、都合のよい混合物です。**

    Goは標準中心、PythonはDjango、JavaはHelidon、RubyはRodaです。それぞれの選択自体は可能ですが、認証や開発速度を比較するなら、Spring Boot・Rails・Phoenixなども別構成として検討する必要があります。

    また、GoではPostgreSQLを推奨しながらSQLiteの高速テストをQ-03の根拠に含めています。**一つの構成で同時に得られない利点を合算しています。**

16. **【重大度：高】DBの性質を、言語の点数として採点している。**

    同時書き込み、日本語検索、バックアップ、制約の多くはDBと運用構成の性質です。同じPostgreSQLでも言語によって検索点が変わるなら、その原因を説明する必要があります。

    BunにS3クライアントやcronがあるからバックアップを加点するのも不適切です。バックアップの評価対象は、整合性・復元可能性・RPO/RTO・鍵管理です。独自実装を減らせるかどうかも含めて比較すべきです。

17. **【重大度：高】メモリ比較が成立していません。**

    Goの認証を無効化した試作の待機RSSと、.NETの認証・DB付きAPIの負荷時RSSを比較しています。版、処理内容、負荷、接続数も違います。

    **同じ機能のアプリ＋DB＋必要な補助プロセス全体**で測るべきです。Goが軽い傾向は認められても、この数字から点差を正当化できません。

18. **【重大度：高】感度分析が、採点の偏りを固定したままです。**

    重みだけ変えても、誤った点数・構成・候補除外は直りません。「C#が1位になる想定がなかった」は、探索した設定の説明にすぎません。

    例えばEF Coreの訂正でC#は427。仮にGoの長期保守を5→3と評価し直すとGoは425です。これが正しい最終採点だとは言いませんが、**重みを変えずとも順位は変わる**ことを示します。

    また「Go 430〜433、Python 426〜430、C# 420〜428で互いに重なる」は数学的に誤りです。GoとC#の区間は重なりません。

19. **【重大度：高】Node.js未評価のままTS候補の位置づけを確定している。**

    TSで書く価値を認めながら、主要な比較対象を省いています。Node.jsを採用すべきという意味ではありません。**未評価なら「上位3候補が確定」とは言えない**という意味です。

20. **【重大度：中】用途との関係が弱い項目で順位を動かしている。**

    LLM APIを呼ぶだけなら、特定ベンダーのSDKの有無による大きな差は説明困難です。日別集計だけならpandasの豊富さも決定打ではありません。「Pythonの学習価値5」「Rubyが逆転する条件はほぼない」も、依頼者の目的や経験なしには決められません。

    事件数や勧告数も、利用規模・開示姿勢・調査密度という分母なしには安全性の順位になりません。

**データベース選定の問題**

21. **【重大度：高】「自前ログインが近いならPGに決まり」は撤回すべきです。**

    認証方式とDBの同時書き込み能力は別問題です。数十人が食事を記録する程度なら、SQLiteも十分な候補です。必要なのは人数ではなく、同時書き込み量・トランザクション時間・配置・可用性要件の確認です。[SQLiteの適用範囲](https://sqlite.org/whentouse.html)

22. **【重大度：中】SQLiteの「書き込み接続一本化必須」「複数プロセスと相性が悪い」は強すぎます。**

    SQLiteは書き手を直列化しますが、複数接続・複数プロセスからの利用自体は可能です。短いトランザクション、待機・再試行、負荷に応じて設計します。`BEGIN IMMEDIATE` や接続一本化は選択肢であり、万能な必須条件ではありません。[SQLite WAL](https://sqlite.org/wal.html)

    WAL-reset修正版への更新は必要ですが、修正済み構成を比較する際に、過去のバグを継続的な並行利用の欠点として二重計上してはいけません。

23. **【重大度：高】PostgreSQLのRLSを、侵害されたアプリからの隔離として過大評価しやすい説明です。**

    RLSの効果は、DBロールと利用者識別情報を誰が変更できるかによります。同じアプリロールが任意の利用者IDを設定できるなら、アプリ侵害後の他人へのなりすましを防げません。テーブル所有者などの迂回条件にも注意が必要です。[PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

    DDLを外しても、DML権限があればデータの大量削除・改変は可能です。防御の価値はありますが、その範囲を限定して書くべきです。

24. **【重大度：中】SQLiteとPostgreSQLの二択は合理的な絞り込みですが、他DBの失格理由は雑です。**

    MySQLとMariaDBは別製品として評価すべきです。TIMESTAMPの制約だけで日時保存全般を不適格にできませんし、RLSが今回必須とも定義されていません。逆に、既存のMySQL運用資産がなければ、候補を増やさない判断は可能です。

    「要件を満たさない」と「今回は積極的に選ぶ理由が少ない」を区別してください。libSQLとTursoも、製品・エンジン・版を特定しない一括評価では成熟度を判断できません。

25. **【重大度：中】バックアップと更新手順の断定が強すぎます。**

    日次バックアップは、失敗を検知し、実際に毎日成功して初めて「最大約1日」の損失目安になります。月次復元訓練の頻度はRPO/RTOと運用負担から決めるべきです。

    またPostgreSQLの小版リリース周期を、そのまま「3か月ごとに更新すればよい」としてはいけません。緊急修正は別扱いです。[PostgreSQLの更新方針](https://www.postgresql.org/support/versioning/)

**このアプリで本当に重要なのに、評価が薄いもの**

26. **【重大度：高】栄養記録の履歴整合性が抜けています。**

    商品マスタを修正したら、昨日食べた記録のカロリーまで変わる設計でよいのでしょうか。食事記録に栄養値のスナップショットを持つか、商品情報を版管理するかが必要です。

    さらに、OFF取得値・手入力・LLM推定値の出所、確認済みかどうか、更新時の優先順位、共通商品と個人用補正の区別が必要です。これは言語の1点差より重要です。

27. **【重大度：高】「NULLと0を区別」で正しさの議論を終えている。**

    SQLの `SUM` は通常NULLを除外します。食塩不明の商品を含む日に、既知分の合計だけを「本日の食塩」と表示すると過小表示になります。合計値と同時に、欠損件数や「不完全な合計」であることを扱う必要があります。[PostgreSQL集計関数](https://www.postgresql.org/docs/current/functions-aggregate.html)

    また、100g／100ml／一包装／一食、摂取量、ナトリウムと食塩相当量、丸める時点を仕様化すべきです。`*float64` を使うだけでは解決しません。

28. **【重大度：高】認可・同期・復旧の実装コストが不足しています。**

    `user_id` 列を付けるだけでは利用者間の分離はできません。全APIでの所有権確認、重複送信への冪等性、編集競合、オフライン同期時の削除伝播、バックアップから復元した後の整合性が必要です。

    UUIDv7も競合解決を提供しません。LLM呼び出しをDBトランザクションの外に置く、といった設計の方が、SQLiteの書き込み制限には直接効きます。

29. **【重大度：中】実装・配備の信頼範囲が不足しています。**

    npmのビルド、CI Actions、コンテナ基盤、cloudflared、バックアップツール、秘密情報の保存場所も評価対象です。`sqlc`を別モジュールに置いても、それだけで実行権限や秘密情報へのアクセスは隔離されません。

    また、digest固定と自動セキュリティ更新を両立させるには、digest自体を更新・検証する工程が必要です。「固定する」「自動再ビルドする」の二文だけでは完成しません。

**結論をどう変えるべきか**

**【重大度：高】「Go＋PGを既定」から、「要件と脅威モデル別の条件付き候補」に変更すべきです。** このレポートの点数を微修正して、別の言語を1位にするだけでは同じ問題を繰り返します。

| 条件 | 優先して検証する構成 |
|---|---|
| 開発時の自動コード実行経路を減らしたい。軽量配備を重視し、Accessを継続する | Go。DBはSQLite／PostgreSQLを別途比較 |
| 認証・入力検証・マイグレーションを既存部品に任せたい | ASP.NET Core＋EF Core |
| CRUD・管理機能を早く完成させたい | Django。現行LTS開始案も含める |
| TS統一が大きな価値を持つ | Node.jsの支援対象LTS構成を追加し、Bunと比較 |

DBは次の条件で判断できます。

- **ローカルディスク、単一ホスト、短い低頻度の書き込み、運用部品を減らしたい**なら、SQLiteを優先検証する。
- **複数ホスト、継続的な書き込み競合、DB接続者ごとの権限分離、既存のPG運用経験**があるなら、PostgreSQLを優先検証する。

これはSQLiteの確定ではありません。**認証の有無やGoドライバへの印象だけでDBを決めるのをやめる**という修正です。

試作比較には、認証、他ユーザーへのアクセス拒否、栄養値の欠損集計、商品修正後の履歴保持、バックアップ復元まで含めてください。認証なしの最小APIのRSS競争では、このアプリの選定材料として不十分です。

**依頼者に確認すべき質問**

| 優先度・重大度 | 質問 | 結論に必要な理由 |
|---|---|---|
| 高 | 最も避けたい被害は、開発機の秘密情報流出、食事データの漏えい、改ざん、消失のどれか | 防御箇所と技術選定の重みが変わる |
| 高 | 自宅サーバーのOS、CPU、実際の空きメモリ、保存先、同居サービスは何か | 配備可能性と資源制約を確定する |
| 高 | Cloudflare Accessを継続できるか。自前ログインとは外部IdP連携か、パスワード管理まで自作する意味か | 認証の開発・保守負担が大きく変わる |
| 高 | 商品情報を修正したとき、過去の食事記録も修正したいか | データモデルと集計仕様が変わる |
| 高 | 不明な栄養値を含む日の合計をどう表示したいか | 数値の正しさの受け入れ条件になる |
| 高 | 許容できるデータ損失時間と停止時間はどれくらいか | DB名よりバックアップ構成に直接効く |
| 中 | 書ける言語に加えて、保守・復旧できるDBや配備環境は何か | 初期学習より継続運用への影響が大きい |
| 中 | オフライン記録・複数端末同期は必須か、将来案か | APIとデータモデルの難度が変わる |
| 中 | 毎月の更新作業と、認証・セッション・移行処理の自作に、どれだけ時間を使えるか | 「依存を減らす」代償を判断できる |
| 中 | 手入力した商品情報は個人専用か、利用者間で共有するか | 所有権、修正権限、出所管理が変わる |

現時点で支持できるのは、**Goも有力、DjangoもASP.NET Coreも有力、DBは未確定**までです。「Goの供給網上の利点」を「dieyet全体の技術的最適性」に読み替える根拠は、このレポートには足りません。
