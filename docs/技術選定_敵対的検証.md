### 認証・認可

**M1 外部 OIDC でも Go では認証の大半が手書き**（3 章参照）
- Go のままで: (1) go-oidc を使う場合は state・nonce・PKCE（S256ChallengeOption）・ログイン時のセッション ID 再生成・サーバー側失効・__Host- 接頭辞の Cookie・http.CrossOriginProtection の配線を受け入れテストに明記する。(2) 標準ライブラリだけで書く構成も検討する: 認可コードフローではトークンエンドポイントから TLS で直接 ID トークンを受け取るので、OIDC Core §3.1.3.7 規則 6 により署名検証を TLS に委ねられ、iss／aud／exp／nonce は JSON の照合だけで済む。Google はこの経路、GitHub は x/oauth2＋GET /user、LINE は POST /oauth2/v2.1/verify（署名・iss・exp・aud・nonce を検証する）。これで本番の第三者は DB ドライバ 1 主体になり SC-01 は 5。(3) LINE は初版から外す（email 権限は申請制、チャネルの Published 化は不可逆）。(4) 試作の認証項目を「Access の JWT 検証」から「実際の OIDC ログイン、他人の sub での拒否、セッションの失効、鍵更新後も既存セッションが読める、ログアウト後の Cookie 再利用の拒否」に差し替える。

**M20 email で突合すると乗っ取り（nOAuth 型）**
- 指摘: Google／GitHub／LINE を同じ OIDC 実装で扱える前提は誤り（GitHub は id_token を発行しない）。email でアカウントを探す実装だと、攻撃者が自分の GitHub／LINE に被害者の Google アドレスを設定して被害者の記録を読み書き・削除できる。Google のディスカバリに end_session_endpoint は無く、6 か月未使用の OAuth クライアントは自動削除される。
- 出所: security APPSEC-2、codex 05。根拠: OIDC Core §5.7「email 等を一意識別子に使ってはならない（MUST NOT）」、Google「Always use the sub field」、GitHub の /user と /user/emails（verified フラグ）、Descope nOAuth、Google Auth Platform の告知。LINE の ID トークンに email_verified は無い。
- 最も強い再反論: Google は email_verified、GitHub は verified フラグを出すので、検証済みメールだけで突合すればメールボックス乗っ取りと同等の難度になる。ただし LINE に verified 相当が無いので「全プロバイダで安全な email 統合」は作れず、禁止という結論は変わらない。初版をプロバイダ 1 つにすれば複数紐付けの設計は後回しにできる。
- 判定: confirmed。言語は変えない（どの言語でも同じ欠陥を作れる）。
- Go のままで: 利用者の主キーは (issuer, sub)（GitHub は数値 id）、email は表示用、email による自動統合を禁止、複数プロバイダの紐付けはログイン済みセッション内の明示操作だけ。受け入れテストに「他人の sub で同じ email を名乗ってもデータに触れない」を追加。プロバイダ喪失時の復旧（第 2 プロバイダの事前紐付け、データ書き出し）、アカウント削除、ログアウト（アプリ側セッション失効のみ）を仕様に入れる。Google クライアントの 6 か月無使用削除を監視。決定文書 L42 の「アプリ側のコードはどちらでもほぼ同じ」を削る。

**M9 「本人のデータか」の確認を 1 クエリずつ手書きする Go＋SQLite は安全網が薄い**
- 指摘: EF Core のクエリフィルタ（所有者・soft-delete を全クエリに自動適用）、concurrency token、SaveChanges interceptor、PG の RLS のような「全クエリに自動で効く」層が Go 標準には無く、SQLite には RLS が無い。所有者条件を忘れた 1 クエリがそのまま IDOR になる。

- 最も強い再反論: EF のフィルタは読み取り側にしか効かず、ユーザーが最優先に置く「改ざん・削除」は書き込み側の被害。書き込み側の防御（所有者はセッションから決める、追記専用、権限の縮小）は EF でもアプリの規律か DB 制約で作るしかなく、DB 制約（GRANT・トリガー・RLS）はアプリ層の interceptor より強く言語非依存。「Go には ORM が無い」は不正確（ent の privacy policy は全クエリに効く。標準ライブラリ中心という方針が除外しているだけ）。Django にも所有者の自動フィルタは無い（未確認）。
- 判定: partially。DB-03 の重み 4＋C# 5 を入れても Go 370／C# 380（R）で揺れの中。
- Go のままで: 決定文書 L110「Go ならどちらでもよい」を条件付きにする（8 章）。リポジトリ層で UserID を専用型の必須引数にし *sql.DB を直接触らせない、CI で sqlc の各クエリが user_id パラメータを持つことを検査、エンドポイント×他人 ID のテスト（20 件程度）、記録テーブルは追記専用（削除は墓石行の INSERT、SQLite なら BEFORE UPDATE／DELETE で RAISE(ABORT)、PG なら UPDATE／DELETE を GRANT しない）、マイグレーションは SQL スクリプトをレビューしてから適用。

**M10 「不明」と「0」の区別が Go の既定の JSON 経路では黙って崩れる**
- 指摘: encoding/json（v1 API）は null を無視し、キー名の大文字小文字違いを受け入れ、未知キーを捨てる。json/v2 も null をゼロ値にし、required タグは無い。AI が書く構造体は素の float64 になりがち。Q-01 の Go は 2 が妥当。

- 最も強い再反論: 比較が「Go の素の標準ライブラリ」対「他言語の検証ライブラリ／コンパイル時の型」で釣り合っていない。TS の JSON.parse は any で欠損は NaN になる、C# の STJ もキー欠落は既定で 0（required 修飾子が要る）、Python は TypeError で落ちる。Go は追加の公開主体ゼロで検証を書け、危険域は入力 1 か所と集計 1 か所。json/v2 は既定で case-sensitive（反論の「v2 も無視」は誤り）。
- 判定: partially。Q-01 は 3 のまま（2 にしても Go −4 で順位不変）。
- Go のままで: 栄養値の入力は全部 *float64（または Nutrient 型）、encoding/json/v2 を直接使い RejectUnknownMembers(true)、v1 を使うなら DisallowUnknownFields＋MatchCaseSensitiveNames、必須 5 項目の欠落は検証層で 400、保存は整数（mg、0.1 kcal）、丸めは表示直前、日別集計は「既知の合計・不明件数・完全か」の 3 値。受け入れテストに「salt を省略／null／Salt／sodium で送ったら 400 か『不明』になり 0 にならない」。「栄養値に素の float64 を使わない」を lint で機械検出。

## 8. DB の推奨（Go 前提）

**既定: SQLite（ncruces/go-sqlite3、CGO_ENABLED=0）。条件付き。**

理由: ユーザーの最優先が「各アプリの軽さ」で、Go＋SQLite は実測 19MB（cgroup 15MiB）、単一バイナリ＋ファイル 1 つで配備・バックアップ（VACUUM INTO／backup API で整合性のある取得）・復元が単純。アプリごとに PostgreSQL を立てるのは最も重く（PG の常駐分は未測）、評価レポート 2.5 の「この規模・単一ホストなら両方要件を満たす」は変わらない。

条件（これを満たせないなら PG）:
1. 保存先はローカルディスク（NAS の NFS／SMB では使わない）。
2. リポジトリ層に集約し、UserID を専用型の必須引数にして *sql.DB を直接触らせない。CI で各クエリが user_id を持つことを検査し、エンドポイント×他人 ID の拒否テストを書く（M9）。
3. 記録テーブルは追記専用（削除は墓石行の INSERT、UPDATE／DELETE は BEFORE トリガーで RAISE(ABORT)）。履歴は本体と同じトランザクションで書く。
4. バックアップは VACUUM INTO → age で暗号化 → アプリから削除できない先（PBS の Datastore.Backup のみのトークン、または R2 の書き込み専用トークン＋bucket lock）へ。別障害領域に置き、復元を試験する（M15）。
5. SetMaxOpenConns(1)（または読み書き別プール）、busy_timeout、_txlock=immediate、WAL。時刻は UTC の RFC 3339 文字列か Unix 秒の整数で自分で明示保存（M8／M19）。
6. マイグレーションは SQL スクリプト（12 段階手順）をレビューしてから適用し、試作で 1 回実際に書いて巻き戻しをテストする（DJ-5）。
7. ncruces の保守が止まったら固定した版を使い続けるかフォークする方針を README に書く。

**全アプリで共有する PostgreSQL を選ぶべき場合**: (a) 「改ざん・削除」を言語ではなく DB 層で守りたい（アプリ用ロールは DML のみ・BYPASSRLS 無し・テーブル所有者でない、全利用者テーブルに RLS、リクエストごとに SET LOCAL で利用者 ID、履歴テーブルは INSERT のみ GRANT し別ロール所有の SECURITY DEFINER トリガで書く）。(b) 質問 7（Grafana／Metabase から直接読む）が「はい」。(c) 他のアプリのために共有 PG を立てる予定が既にあり、常駐分を多数のアプリで割れる。その場合は pgx（govulncheck を CI に）、アプリごとのロールとスキーマ、資源制限は PG ではなく LXC 側で行う（PG のロール単位の資源制限は接続数と statement_timeout 程度。未確認）。アプリごとの PostgreSQL は推奨しない。

**最も強い反論（SQLite 既定に対して）**: ユーザーが最優先に挙げた被害は「改ざん・削除」であり、SQLite はアプリと同じプロセスで動くので、アプリが乗っ取られれば履歴もトリガーも同じ権限で無効化できる。PG＋DML のみのロール＋RLS＋履歴の別ロール書き込みは「アプリの論理の誤りによる漏れ」と「アプリ権限での履歴改ざん」を DB 層で止められ、SQLite にはこの第 2 層が無い（M9、M15、評価レポート 2.2）。さらに Go＋SQLite の最大依存は 1 人保守の機械生成コードで差分レビューができず、PG 側の pgx は読める（M8）。これに対する答え: SQLite でも追記専用トリガーと外部の削除不能バックアップで「乗っ取り後の改ざんを検知して復元できる」状態は作れるが、「乗っ取られたアプリが同じ DB サーバー内で止められる」状態は作れない。改ざん防止を軽さより上に置くなら共有 PG が正しく、それはユーザーの優先順位（質問 2 の答えは両方）の中での順序付けの問題で、本判定では決められない。利用者ごとに SQLite ファイルを分ける案（個人記録は構造的に他人のファイルに届かない。商品マスタは共有 DB に分離）は、軽さを保ったまま漏れの面積を減らす中間解。

## 9. Go 以外を選ぶべき条件（こうなら逆転）

- **C#（.NET 10 LTS、ASP.NET Core Minimal API、PG 経路）**: 修正後の点は既に C# 372／Go 367 で同点圏なので、逆転条件は点ではなく代償の引き受け先。次の 3 つがそろえば C#: (1) OIDC クライアント・セッション・CSRF・マイグレーション・保守画面を手書きしたくない（Microsoft 一次提供の OIDC ハンドラ（PKCE 既定、PAR 既定）、Cookie 認証、Data Protection の鍵 90 日更新、EF のクエリフィルタと差分マイグレーション）、(2) 月次の再ビルド CI を作る気が無く、LXC に aspnetcore-runtime-10.0 を apt で入れて unattended-upgrades＋サービス再起動の自動化に任せたい（Ubuntu の本家 feed は Canonical が Ubuntu の寿命まで支援）、(3) 1 アプリ RSS 115〜120MB（私有約 46MB。EF なら +40MB と 2 倍の遅さ）を払える。条件: PG 経路（SQLite 経路は SQLitePCLRaw の .targets と .so を本番依存に加える）、nuget.config に signatureValidationMode=require＋trustedSigners（Linux での動作は要実機確認）、packages.lock.json＋--locked-mode、テストは MSTest（xunit は Microsoft 以外の analyzers が動く）、Renovate の minimumReleaseAge、2028-11 までに .NET 12 への移行。GitHub／LINE のログインは Microsoft 一次提供ではなく aspnet-contrib か自前設定が要る点は Go と同じ。
- **Django（Python 3.14、Django 6.2 LTS、SQLite）**: Python を書けて MVP の速さを優先する（R で Django 390／C# 386／Go 381）か、共有の商品マスタの監修画面を初版の必須要件にする（ADM-01 を重み 5 で足すと Django 396／Go 391）場合。条件: 1 アプリ +70MB（1 ワーカー 85MB）と 2026 年 8 回・32 CVE の月例追従、uv の no-build＋exclude-newer 7 days＋--frozen、OIDC クライアントを標準ライブラリで書くか allauth（公開主体が 7 以上に戻る）を入れるかを決める、OS の SQLite 版（Debian 13 は 3.46.1）を避けて uv 管理の CPython（3.53.1 同梱）を使う、/admin は Cloudflare Access の後ろに置く、Astral の買収（承認待ち）を注記。
- **TypeScript（Node 26 LTS、node:sqlite、openid-client）**: 質問 5「画面と同じ TS／オフラインで動く記録・集計・同期のロジックを 1 回だけ書きたい」に「はい」の場合（R で C# 393／Node 389／Go 386／Django 383 と同点圏に入る。Go＝Node ではなく C# が先頭）。条件: Node 26 同梱の npm は 11.20.0 なので npm 12 か pnpm 11 を別途入れる、min-release-age（pnpm は minimumReleaseAge 10080）、strict-allow-scripts、CI で npm ci＋npm audit signatures、PR に秘密を渡さない、サーバーの第三者は panva 1 主体（PG なら porsager を追加。provenance 無し）、node:sqlite の RC（Stability 1.2）を受け入れる、1 アプリ 75〜85MB。Bun は LTS 無し・Security Advisories 非公開・Anthropic 所有（利益相反）で本命にしない。
- **既製バックエンド（PocketBase、Go ライブラリ構成）**: 「数週間早いデモ」と「認証・CRUD・管理画面を書かない」を、本番経路の公開主体 17、1 人保守の pre-1.0（後方互換の約束無し、minor 33 回中 13 回に breaking）、NULL を持てない number 列、SQLite 固定より上に置き直す場合だけ。ユーザーの現在の重みでは 37〜40 点届かず、SEC-03 を 4 に戻しても OPS-01 を同点にしても MVP 最速にしても差は 30 点以上。試作で 1 列比べてから決める。

## 10. ユーザーに確認すべき質問（結論を左右するものだけ、優先度順）

1. **開発用 PC の保護を「言語の重み」で買うか。** 隔離した環境（トークンを置かない VM／devcontainer、画面側 npm も同じ環境、拡張の棚卸し）を本当に運用するなら SC-02 の重みは評価レポートの 3 に戻す（→ Go・C# 同点圏）。運用しないなら 5 のまま（→ Go 先頭）。「運用しない」は L74 の決定と矛盾するので、実質は「隔離を運用するか」の確認。
2. **1 アプリあたり +40〜80MB（16GB の 0.25〜0.5%、10 アプリで 0.4〜0.8GB）に重み 5 を置き続けるか。** 置き続ける → Go は同点圏の先頭か同点。3 以下 → C# が先頭（差は揺れの中）。
3. **代償をどちらで引き受けるか。** Go: 手書きの OIDC クライアント・セッション・CSRF・認可・マイグレーション・保守画面（100〜200 行＋テスト）と、月次の自動再ビルド CI。C#: 共有フレームワークの apt 更新と Microsoft 製部品、1 アプリ +40〜80MB、NuGet の署名運用。この答えが点より順位を決める。
4. **質問 3（習熟度）**: Python を書けるか。C# は。TS は。Python を書けて MVP を急ぐなら Django が先頭。
5. **質問 5 の言い換え**: オフラインで動く記録・集計・同期のロジックを 1 回だけ書きたいか。「はい」なら Node 26 LTS を試作対象に加える。
6. **手入力・ラベル撮影の商品データは個人用か、利用者間で共有して監修するか**（評価レポート 3.2 の質問 3）。共有なら監修 UI・来歴・版固定が要件になり Django が 1 点差まで寄る。Go なら保守画面の工数を試作で数える。
7. **質問 6（RPO／RTO）と、改ざん防止を軽さより上に置くか。** 上に置くなら共有 PG＋RLS。バックアップ先（PBS か R2）と権限分離をここで決める。
8. **初版のログインは Google 1 つでよいか。** LINE は初版から外す（email 申請制、Published 化不可逆、HS256）。GitHub は OAuth2 の別経路。
9. **保存先はローカルディスクか NAS か**（SQLite の可否）。
10. **質問 7（Grafana／Metabase から DB を直接読みたいか）**。「はい」なら共有 PG 寄り。

言語に関係なく、確定前に最初にやること: 実機 iPhone でホーム画面 PWA のカメラ読み取りを 1 週間検証する（許可ダイアログの頻度、近接時の合焦、zxing-wasm のデコード時間、JAN の誤読率）。デモの成否を最も左右するのはここで、Go の保存 API は並行して作れる。
