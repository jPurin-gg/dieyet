## 0. 結論

- **推奨（暫定）: C# 14／.NET 10 LTS（10.0.13）＋ASP.NET Core Minimal API＋EF Core 10（10.0.13）＋Npgsql 10.0.3＋PostgreSQL 18。** MVP の認証は、Cloudflare Access の JWT を JwtBearer で検証する。自前ログインが要る段階では、ASP.NET Core Identity（パスキー対応 [S30]）か OpenID Connect で組む。
- **確度は低い。** 修正後の合計（満点 470）は C# 364、Django 359、Go 358。争点の採点を ±1 動かすと、幅は C# 352〜379、Django 343〜370、Go 338〜362 で重なる。C# を既定にした理由は点差ではない。Microsoft 以外の本番依存を Npgsql 1 つに抑えたまま、将来の自前ログイン、CSRF 対策、マイグレーションを自作せずに済むことが理由。
- **次点: Go 1.27（標準ライブラリに pgx か ncruces/go-sqlite3）と、Python 3.14＋Django 5.2 LTS／6.2 LTS（標準の sqlite3）。**
- **逆転条件:** 自前ログインを作らずに Cloudflare Access（無料枠は 50 人まで [S28]）を使い続け、かつ開発機の保護を最優先にするか、サーバーが低スペックなら Go。Python を書けて MVP の速さを優先するなら Django。画面と同じ TS を最優先するなら Node.js 24/26 LTS だが、暫定の採点は 332 点にとどまり、実測を含めて評価し直す必要がある。
- **DB は認証の有無では決めない。** この規模で単一ホストなら、SQLite も PG も要件を満たす。C# で PG を既定にするのは、SQLite の経路を選ぶと、1 人が保守するネイティブの SQLite と、ビルドのたびに読み込まれる .targets が本番依存に加わるから。Django なら SQLite、Go ならどちらでもよい。確定の前に、上位 2〜3 構成で 3.4 の試作（認証、他人のデータへのアクセス拒否、欠損値の集計、履歴の保持、復元）を作り、自宅サーバーで実測して決める。

直した点の根拠:

- SC-01: Django 構成の公開主体は 7（1.3）。Ruby（Roda＋Sequel＋Puma ほか）も 4〜7 の帯に入ると推定した（評価者の依存の一覧から数えた推定）。

- DB-06（C#/EF）: EF Core は「現在のモデルを古いモデルのスナップショットと比べ、マイグレーションのソースを生成する」[S13]。
- 据え置いた点: C# の SC-04 は 3 のまま。govulncheck のように、脆弱な関数が実際に呼ばれるかまで調べる仕組みが無いため。各候補の OPS-01 も草案の点のままにし、代わりに重みを下げた。Go の Q-03 は DB を除いても 5 のまま。根拠は httptest と testing/synctest による仮想時間で、SQLite のテストの速さではない。

## 2. DB の比較と結論

### 2.1 判断の基準

Codex が示した条件を採用する（Codex 21）。

- **SQLite を先に検証する条件:** DB をローカルディスクに置ける、ホストが 1 台、書き込みが短くて少ない、運用の部品を減らしたい。
- **PostgreSQL を先に検証する条件:** ホストが複数、書き込みの競合が続く、DB に接続する者ごとに権限を分けたい、PG の運用経験がある、Grafana や Metabase から DB を直接読みたい。
- **判断に使わないもの:** 認証の有無。SQLite 公式は「1 日 10 万ヒット未満のサイトなら、たいてい問題なく動く」とし、選び方として「ネットワーク越しにデータを置くか」「同時に書く者が多いか」「データが大きいか」を挙げている [S21]。数十人が食事を記録する程度なら、自前ログインを作っても SQLite で足りる。

このアプリは、ホストが 1 台で書き込みが少ないので、**作業負荷の面ではどちらでも要件を満たす。** 差が出るのは、言語との組み合わせ（2.4）と、運用の好みと、保存先の種類。

### 2.2 SQLite と PostgreSQL

| | SQLite（3.51.3 以上） | PostgreSQL 18 |
|---|---|---|
| 主な長所 | DB 用のプロセス、ポート、認証情報が要らない。テストが速い。backup API や VACUUM INTO で、稼働中でも一貫したコピーを取れる。FTS5 の trigram で 3 文字以上の部分一致に索引が効く（DB 評価者の確認） | 型と制約が厳格で、DDL もトランザクションで巻き戻せる。同時書き込みに強い。メジャー版ごとに 5 年支援（18 は 2030-11-14 まで [S23]）。ドライバの多くは通信手順を実装しただけのコード。pg_dump だけでバックアップを始められる |
| 主な短所 | 書き手は常に 1 つ [S3]。短いトランザクション、busy_timeout、BEGIN IMMEDIATE、書き込み接続の一本化は、負荷に応じて選ぶ手段で、どれも必須ではない（Codex 22）。読み手は別プロセスでもよいが、同じホストに限られる。WAL はネットワークファイルシステムでは動かない [S3]。型と外部キーは既定で緩い（STRICT と PRAGMA foreign_keys が要る）。DB のロールが無い。エンジンの版はドライバ、ランタイム、OS のライブラリの側で決まる | コンテナ、認証情報、メモリ（待機時に数十 MB とされる。要実測）が増える。小版は「少なくとも 3 か月ごと」に出て、重大な修正は周期の外でも出る [S23]。5 年以内にメジャー更新が要る（18 で公式 Docker イメージのボリューム構成が変わった。DB 評価者の記載）。テストに DB のコンテナが要る。日本語の検索に要る pg_bigm や PGroonga は公式イメージに入っていない（DB 評価者の記載） |
| 必ず守ること | 起動時に sqlite_version() を確かめ、3.51.3 以上（または修正を取り込んだ 3.50.7・3.44.6）でなければ起動しない。WAL-reset バグは、3.7.0〜3.51.2 で、2 つ以上の接続が同時に書き込みかチェックポイントをしたときに DB を壊しうる [S3]。修正済みの版なら、複数の接続やプロセスで使うこと自体は問題ない（過去のバグを二重に数えない） | ポートを公開しない（Docker の -p は ufw を迂回する。DB 評価者の記載）。SCRAM 認証を使う。アプリ用のロールは DML だけにする。小版は告知を見て追従する |
| 権限分離の限界 | アプリと同じプロセスで動くので、アプリが乗っ取られれば DB も丸ごと取られる | 同じく限界がある。superuser と BYPASSRLS を持つロールは RLS を常に迂回する。テーブルの所有者も、FORCE ROW LEVEL SECURITY を付けない限り迂回する [S22]。RLS が参照する利用者 ID をアプリが設定する方式では、乗っ取られたアプリは他人になりすませる。DML の権限があれば、データの大量削除や改変もできる。防げるのは主に、DDL などの権限外の操作と、アプリの論理の誤りによる漏れ（Codex 23） |

### 2.4 言語との組み合わせ（公開主体の観点）

草案は「Go の SQLite ドライバは人が読めない、pgx は読める」を PG を選ぶ理由にしていた。Codex 12 の指摘どおり、PG 本体、その Docker イメージ、OS も信頼の対象で、読むかどうかだけでは比べられない。ここでは、**誰の公開物が本番とビルドの経路に入るか**で比べる。

| 言語 | SQLite の経路 | PostgreSQL の経路 | 既定 |
|---|---|---|---|
| C# | Microsoft.Data.Sqlite の下で、SQLitePCLRaw（作者は Eric Sink の 1 人）のネイティブの SQLite が動く。lib.e_sqlite3 の 2.1.13 と 3.53.3 は buildTransitive に .targets を持ち、ビルドのたびに読み込まれる。2.1.13 の net9.0 向けの中身は wasm 用の参照を足すだけで無害だが、乗っ取られれば任意のコードを実行する経路になる（パッケージの中身を一覧して確認 [S33]） | Npgsql 10.0.3 と、その EF Core プロバイダには build、buildTransitive、analyzers の資産が無い（同上）。PG サーバーは公式 Docker イメージで入れる | **PG** |

| Bun | bun:sqlite（内蔵） | Bun.sql（内蔵。未実装の機能がある） | どちらでもよい |

### 2.5 結論

- DB は**言語と一緒に決める。認証の有無では決めない。** 推奨の C# では PostgreSQL 18 を既定にし、SQLite（Microsoft.Data.Sqlite）も許容する。SQLite にするなら、SQLitePCLRaw のネイティブ部品と .targets を受け入れることになる。ExcludeAssets で buildTransitive を外しても Linux で動くかは要検証。
- 運用の部品を最小にすることを何より優先するなら、SQLite を選ぶ。その場合は Django（標準の sqlite3）か Go（ncruces）と組むのが自然。
- 保存先が NAS（NFS や SMB）なら、SQLite は使えない。PG のデータを NAS に置く場合の注意点は要確認。

### 2.6 運用で必ずやること（どちらの DB でも）

- **バックアップ:** 日次でダンプ（PG は pg_dump、SQLite は VACUUM INTO）を取り、age などで自分で暗号化して R2 に置く。失敗を検知して通知する仕組みを付けたときに初めて、「失うのは最大でおよそ 1 日分」と言える（Codex 25）。数秒の RPO が要るなら、Litestream か PG の WAL アーカイブを使う。Litestream 0.5 系は、自分の側で暗号化する age の機能が削除されている [S43]。pgBackRest は 2026-04-27 に保守の終了が告知され、5 月 18 日に支援企業の連合で継続が決まった。最新の 2.59.3（2026-10-04）では、暗号化に使う副鍵が弱くなりうる不具合が直された [S44]。
- **リストアの訓練:** 頻度は RPO/RTO と運用の手間から決める。草案の「月 1 回」は一つの目安にすぎない。別のコンテナに戻し、件数とチェックサムを照合する。
- **更新:** PG は小版の告知を見て追従し、周期の外の重大な修正にもすぐ当てる。SQLite は、起動時に版を確かめることで、ドライバやランタイムの更新を追う。

## 3. どの構成を選んでも必要なこと（言語の 1 点差より大きい）

### 3.1 脅威モデルの修正

ユーザーの「画面側の npm 依存は、バックエンドとの通信を厳格にすれば許容する」という前提は、**利用者のデータを守るには足りない**（Codex 1）。悪性の JS が正規の画面に混入すれば、同じオリジンで、ログイン中の利用者として API を呼べる。OWASP も、HttpOnly は Cookie を JS から読めなくするだけで、「XSS を止めず、スクリプトの実行も止めない」と書いている [S5]。バックエンドの言語を分ける価値は、主にサーバーの実行環境と秘密情報、全利用者のデータを守ることにある。

| 攻撃の経路 | 起きること | 主な対策 | 言語の選択が効く度合い |
|---|---|---|---|
| 画面の npm 依存の乗っ取り | 利用者として API を呼び、記録を読み書きする | 依存を最小にする（zxing-wasm などに限る）。ロックファイルと待機期間を使う。npm 12 の既定（install scripts を実行しない。二次情報 [S47]）を保つ。CSP で script-src を自分のオリジンに限る（WebAssembly に要る許可の最小値は要確認）。外部の CDN を使わない。ビルドは秘密情報の無いコンテナで行い、成果物の差分を見る | ほぼ効かない |
| サーバーの依存の乗っ取り（実行時） | 全利用者のデータ、DB・R2・LLM の秘密情報が漏れる | 公開主体を減らす（SC-01）。版を固定し、待機期間を置く。コンテナの権限を最小にする。サーバーに置く秘密情報を最小にする | 中（公開主体の数で差が出る） |
| 開発機と CI での依存のコード実行 | GitHub、Cloudflare、LLM の鍵が漏れる | テスト、ビルド、IDE は、秘密情報の無い隔離環境（devcontainer か VM）で動かす。Go でも go test はテストのバイナリを作って実行する [S6]。CI は PR に秘密情報を渡さず、Actions は SHA で固定する | 小〜中（差は取得・ビルドの段階だけ） |
| 自分のコードの欠陥（認証、認可） | なりすまし、他人のデータの閲覧や改ざん | 一次提供の部品を使う。全 API で所有者を確かめる。他人のデータへのアクセスを拒否するテストを書く（3.3） | 中〜大（一次提供の厚さで差が出る） |
| 配布経路での改ざん | すり替えた版を取得する | ハッシュの固定（lock、sum）、署名の検証、透明性ログ。sumdb が保証するのは「同じ版は誰にとっても同じビット」であることで、中身の安全ではない [S7] | 小 |
| 正規アカウントの乗っ取りで出た悪性版 | 本物として配られる悪性版を取得する | 待機期間を置く。差分を確かめる。依存を減らす。公開する側の Trusted Publishing と 2FA（PyPI も推奨 [S38]）は、別の経路に効くので軽視しない。govulncheck は既知の脆弱性を調べる道具で、悪性コードの検知器ではない [S8] | 小〜中 |
| 外向き通信を使った持ち出し | 許可した宛先（LLM API や OFF の書き込み API）や DNS を通じて持ち出す | 許可リストはネットワークの層で強制する。HTTPS_PROXY などの環境変数は、無視して直接接続すれば迂回できる。DNS も絞る。OFF の書き込み用の資格情報をサーバーに置かない。LLM は別のプロセスに最小限のデータだけを渡す。Deno の権限も、同じスレッドのコードは同じ権限を持ち、依存ごとには分けられない [S9]。Node の Permission Model は「悪意あるコードからは守らない」と明記している [S10] | 小 |
| 基盤（コンテナのベースイメージ、cloudflared、バックアップの道具、秘密情報の置き場） | 同上 | イメージを digest で固定し、Renovate の digest 更新の PR で検証つきで上げる [S26]。cloudflared の版を管理する。秘密情報はファイルの権限を絞って置く | 効かない |

Cloudflare Access の JWT は、cloudflared の側でも検証させて二重にできる（originRequest の access [S29]）。オリジンの側の検証では、aud と iss を確かめる。鍵は既定で 6 週ごとに回り、古い鍵は 7 日間有効 [S27]。

### 3.2 栄養データの正しさ（Codex 26・27）

- **履歴:** 既定では、食事の記録に「記録した時点の栄養値」を複製して持つ。商品マスタを直しても、昨日の記録は変わらない。過去の記録も直したいなら、明示的な「再計算」の操作にする。代わりに商品を版で管理し、記録が版を参照する方式もある。どちらにするかはユーザーが決める仕様（下の一覧）。
- **出所:** 栄養値ごとに、出所（OFF、手入力、LLM による推定、ラベルの写真）、確認済みかどうか、入力者、日時を持つ。値がぶつかったときの優先順位も決める（例: 本人が確認した手入力 > OFF > 確認していない LLM の推定）。共通の商品マスタと、利用者ごとの補正は分ける。
- **基準と単位:** 100g、100ml、1 包装、1 食のどれ当たりかを列で持つ。摂取量は g・ml か「食数」で持つ。比重が分からない液体は換算しない。
- **食塩:** 日本の表示は食塩相当量で、ナトリウム（mg）×2.54÷1000 で換算する（消費者庁のガイドラインを引く自治体の資料 [S25]）。2.5 で換算する資料もある。OFF の salt と sodium がどちらの係数で換算されているかは要確認。表示された値と、換算で求めた値は区別して持つ。
- **欠損:** SQL の SUM は NULL を除いて合計し、対象が 0 行なら NULL を返す [S24]。食塩が不明な食品を含む日に、既知の分だけを「本日の食塩」と出すと過小表示になる。日別の集計は、既知の値の合計、不明の件数、合計が完全かどうかの 3 つを返す。COALESCE で 0 にするのは、表示の直前で「不完全」の印を付けるときだけにする。
- **丸め:** 保存するときは丸めない（例: 整数の mg や 0.1 kcal の単位で持つ）。丸めるのは表示の直前だけにし、その規則を一か所にまとめる。

ユーザーが決める仕様（言語と DB の選定は変えないが、データモデルを左右する）:

1. 商品の情報を直したとき、過去の食事の記録も直したいか。
2. 不明な栄養値を含む日の合計を、どう表示したいか（例: 「≥ 2.1 g（2 品は不明）」）。
3. 手入力した商品の情報は、個人用か、利用者の間で共有するか。共有するなら、誰が直せるか。
4. オフラインでの記録と、複数の端末の間の同期は必須か、将来の案か。

### 3.3 認可、同期、復旧（Codex 28）

- **所有者の確認:** すべての読み書きで、データアクセス層が利用者で絞り込む（例: EF Core のグローバルクエリフィルタ）。RLS は補助として使う。他人の記録を読み書きしようとしたら 404 か 403 になることを、自動テストで確かめる。
- **冪等性:** クライアントが作る ID（UUIDv7）に一意制約を付けて、再送しても二重に登録されないようにする。
- **編集の競合:** version 列か更新日時で楽観的に排他し、ETag と If-Match を使う。UUIDv7 は競合を解決しない。
- **オフライン同期（必須になった場合）:** 削除は墓石（deleted_at）で伝える。競合したときの規則を決める。
- **復元した後の整合:** バックアップから戻すと、端末の側にサーバーより新しい記録が残る。サーバーに世代の番号を持たせ、同期のときに検出する。
- **外部の呼び出し:** OFF と LLM の呼び出しは DB のトランザクションの外で行い、結果を短いトランザクションで書き込む。SQLite の「書き手は 1 つ」という制約にも、これが直接効く。

### 3.4 確定の前の試作と実測

C#/EF と Go で（Python を書けるなら Django も加えて）、同じ薄い試作を作って比べる。認証の無い最小の API でメモリを競っても、選定の材料にはならない（Codex 17）。

- **作る機能:** (1) Cloudflare Access の本物の JWT の検証（aud、iss、exp。鍵の回転への追従を含む）。(2) 商品の取得（自前のマスタ、無ければ OFF。OFF の読み取りは 15 回/分/IP、検索は 10 回/分/IP、独自の User-Agent が必須 [S4]）。(3) 手入力の登録。(4) 食事の記録（栄養値の複製と冪等性）。(5) 日別の集計（不明の件数つき）。
- **受け入れテスト:** 他人の記録の読み書きが拒否される。商品を直しても、昨日の記録は変わらない。食塩が不明な食品を含む日は「不完全」と出る。同じ記録を 2 回送っても 1 件になる。バックアップを別のコンテナに戻すと、件数とチェックサムが一致する。
- **測るもの:** 同じコンテナの制限の下で、ウォームアップした後の待機時の RSS、2,000 リクエストを並列 20 で送った後の RSS（DB のプロセスと補助のプロセスを含めた合計）、イメージの大きさ、最初のビルドと変更後のビルドの時間、書いた行数、ロックファイルから数えた第三者パッケージと公開主体の数。自宅サーバーの上で測る。

### 4.1 C#／.NET 10＋ASP.NET Core＋EF Core の弱点

| メモリが未実測 | 草案の公式の数値は .NET 8 の負荷時の値で、他の候補と比べられない | 3.4 の手順で、自宅サーバーで測る。収まらないときに Go へ切り替える基準を先に決めておく |
| 学ぶ量 | DI、ホスティング、Options、MSBuild、EF Core の概念がある | Minimal API と EF Core だけで始め、他のフレームワークを足さない |
| Cloudflare Access との接続 | Cloudflare の公式のコード例は JavaScript、TypeScript、Go、Python で、C# は無い [S27]。JWKS の取得とキャッシュ、未知の kid が来たときの取り直しを数十行書く | 本物のトークンで試す（要確認）。cloudflared 側の検証と二重にする |
| NuGet の監視の目の薄さ | 2024-08 に公開された悪性パッケージ（ASP.NET Identity のデータを狙う）が報告されたのは 2026-02 で、4,500 回以上ダウンロードされた（報道 [S35]） | 新しい依存を足さない。足すときは、公開者、公開日、ダウンロード数、リポジトリを確かめる |
| EF Core の扱い | NULL の集計の振る舞いは SQL と同じ（3.2）。生成されたマイグレーションを、そのまま流してはいけない | マイグレーションは SQL スクリプトかバンドルにし、レビューしてから DDL 用のロールで適用する（Microsoft の文書も本番ではこの形を勧めている [S13]） |

### 4.2 PostgreSQL を選ぶことの弱点

コンテナ、認証情報、メモリ（要実測）が増える。小版への追従と、2030-11-14 までのメジャー更新が要る（2.2）。テストに DB のコンテナが要る。日本語の 1〜2 文字の検索は索引が効きにくい。RLS とロールで分けられる範囲は限られる（2.2）。PG 本体は、言語のパッケージとは別の配布経路（Docker の公式イメージ）を信頼することになるので、digest で固定する。

### 4.3 次点の構成を選ぶ場合

**Go 1.27（標準ライブラリ中心）**

- 強み: 供給網の群が、開発の終了が決まった Deno を除けば最も高い（75）。取得とビルドの段階で依存のコードが動かず、依存の差分をソースで読める。静的バイナリで、待機時の RSS は最小構成で約 3〜6MB（評価者の実測。認証の無い試作なので他と比べられない）。arm64 と armv7 へのクロスビルドを評価者が実測している。
- 弱み: 自前ログインを作るなら、セッション（失効、固定化対策、鍵の更新）やマイグレーション（同時実行、途中の失敗、適用履歴）を自作するか、第三者の部品を足すことになる（Codex 7）。ゼロ値の文化があり、float64 では JSON の値が欠けても null でも黙って 0 になる。各版の支援は約 1 年で、2026 年はほぼ毎月セキュリティ修正が出た（1.26.1〜1.26.6、1.26.9、1.27.2 [S14]）。go コマンド自体にも、cgo と SWIG の経路でビルド時にコードを実行できる脆弱性があった（CVE-2026-27140、1.26.2 で修正 [S36]）。1 文字違いの偽モジュール shopsprint/decimal は、init() に DNS を使うバックドアを仕込んで約 33 か月配られていた [S37]。
- 選ぶときの要点: JWT は go-jose（か go-oidc）で検証し、自作しない。栄養値は *float64 か sql.Null で受ける。CGO_ENABLED=0 にする。mattn/go-sqlite3 でも、クロス用の C ツールチェーンがあればクロスビルドできる [S17]。

**Python 3.14＋Django**

- 強み: 書く量が最も少ない（ORM による集計、モデルの差分からの自動マイグレーション、管理画面）。認証、セッション、CSRF を一次提供する。DB を後から替えやすい。SQLite なら公開主体が増えない。
- 弱み: 公開主体が 7 で、PyPI は最も狙われる登録所の一つ。2026-03 の LiteLLM と Telnyx の事件では、Trivy 経由で漏れた API トークンで悪性版が公開され、マルウェアはインストール時に動き、隔離までの 2 時間 32 分で 11.9 万回以上ダウンロードされた [S38]（.pth による起動時の実行という経路は、PyPI の報告に記載が無く要確認）。RS256 の検証には、ネイティブの cryptography が要る。ワーカーごとにメモリを使う（要実測）。型の検査は任意で、CI で必須にしないと効かない。
- 選ぶときの要点: 5.2 LTS（2028-04 まで）か、6.2 LTS（2027-04 公開、2030-04 まで）で始める。2028 年以降は毎年 1 月のリリースがそれぞれ 3 年支援される [S16]。uv の lock をハッシュつきで使い、exclude-newer と no-build を設定する（例外は 1.4 の注記のとおり）。起動時に SQLite の版を確かめる。

**Node.js 24/26 LTS（TS の統一を選ぶ場合。暫定）**

- 確かめた事実: 24 は 2026-10-20 から保守 LTS に入り、2028-04-30 まで。26 は 2026-10-28 に LTS に入り、2029-04-30 まで [S19]。27 以降は毎年 1 本で、どの版も LTS になる。型の除去（type stripping）は 24.12 で Stable [S48]。crypto.argon2 は 24.7.0 で追加された [S48]。node:sqlite は Release candidate [S20]。Permission Model は Stable だが、悪意あるコードからは守らないと明記し、--allow-net も宛先を絞れない [S10]。npm 12 は依存の install scripts を既定で実行しない（2026-07 公開、二次情報 [S47]）。Hono、jose、postgres の直接の依存は 0 [S49]。
- 弱み: 型は実行時に消えるので、tsc を CI の必須の関門にし、入力は実行時に検証する。セッションと CSRF は一次提供されない。画面の npm 依存がサーバーに入り込まないかどうかは、構造ではなく設定で守ることになる。

**Bun 1.4**: 部品の内蔵が最も広く、MVP は第三者の依存 0 で作れる。一方で、1.4（2026-08-20）で Zig から Rust に書き直したばかり [S2]。SECURITY.md が支援対象とするのは「1.x.x」だけで LTS は無く、公開済みの Security Advisories は 0 件 [S42]。Anthropic が所有しているので、利益相反がある [S41]。

**Deno**: Deno のチームは Cloudflare に合流し、ランタイムには 1 年間、月次で修正版を出したあと開発を終える。Deno は OSS として残り、他者による開発の継続を歓迎すると明記している [S1]。継続する主体が現れるまでは、新しく長く運用する土台には選ばない。

### 4.4 その他の候補と、採点していない構成

| 構成 | 位置づけ |
|---|---|
| PHP（327）、Java＋Helidon（306）、Elixir（306）、Rust（289）、Ruby＋Roda（289） | 上位との差が大きい。Rust は、標準の構成でビルドされる crate が 155 あり（評価者の実測）、2026-08 の arrayref の事件ではビルドスクリプトが悪性の第 2 段を取得した [S40]。Elixir では、Hex で mix.lock のチェックサムの照合が 0.16.0〜2.4.1 の間、黙って行われていなかった（CVE-2026-32148 [S45]） |

## 7. 限界、利益相反、要確認の事項

### 7.1 この評価の限界

- **採点は 1〜5 の整数で、上位の差はその刻みより小さい。** 0 章の推奨は、点差ではなく条件で選んだ暫定のもの。
- **Node.js の列は暫定。** 筆者が一次資料で確かめた事実だけで付けた点で、試作も測定もしていない。
- **証拠の質に差がある。** 実測があるのは Go と Rust だけで（評価者による）、それも同じ条件では比べられない。メモリは全候補で要実測。
- **重みはユーザーの承認の前のもの。** 1.6 の表で、答えに応じて順位がどう動くかを示した。

### 7.2 利益相反

この文書は Anthropic 製の Claude が書いた。Anthropic は Bun を所有している [S41]。草案で Anthropic の公式 SDK の有無が点に入っていた ECO-02 は、この版で重みを 0 にした。前段で Claude は供給網の一軸で Go を推し、草案でも Go を僅差の 1 位にした。この版では C# が僅差の 1 位になったが、これが反動による過剰な修正でないことは、点ではなく 1.6 の条件と 3.4 の試作で確かめてほしい。

### 7.4 要確認の事項

- 各構成の実際のメモリ（自宅サーバーで、3.4 の手順で測る）。
- Cloudflare Access の JWT の検証を、本物のトークンで試すこと（どの評価者も試していない）。
- Debian trixie の libsqlite3 に WAL-reset の修正が入っているか。Python の公式イメージがどの版にリンクしているか。
- SQLitePCLRaw の buildTransitive を ExcludeAssets で外しても、Linux で動くか。
- nuget.config の trustedSigners の require モードが、Linux の dotnet CLI で完全に働くか（評価者の記載）。
- OFF の salt と sodium の換算係数。
- npm 12 の公開日と既定値の細部（二次情報のみ）。Node の armv7 向けの公式ビルドと、Node 26 での Temporal の扱い。
- CSP で WebAssembly（zxing-wasm）を動かすのに要る最小限の許可。
- PG のデータを NAS の上に置く場合の注意点。
- SQLite から PG への移行が数日で済むという見積もり。
